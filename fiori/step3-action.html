第 F4 章：手顺3 —— Action 与双线集成

把服务 Action 变成页面按钮 · 状态徽标 · RAP 侧 @UI 注解与 Draft

前两章都是「读」数据。本章让页面做事：CAP 侧把 submitOrder Action 变成对象页的「下单」按钮并显示状态徽标；RAP 侧回顾 RAP 手顺4，补齐 CDS @UI 注解与 Draft 机制，完成 RAP / CAP 双线在 Fiori 层的收口。

Action Criticality CDS @UI Draft Service Binding

F4.1 CAP 侧：把 submitOrder 变成按钮

Bookshop 服务在 CAP 手顺3 定义了 bound action submitOrder。Fiori Elements 会自动把服务的 bound action 渲染成对象页按钮区的操作按钮，无需任何注解；但可以借助 @Common 注解控制显隐与文案。先在服务端确认 Action 定义（素材包 srv/cat-service.cds）：

// srv/cat-service.cds —— 既有定义
service CatalogService {
  entity Books as projection on my.Books;
  entity Orders as projection on my.Orders;
  // 绑定到单条 Book 的 Action：减库存 + 记订单
  action submitOrder(book: Integer, quantity: Integer);
}

在 app/books/annotate.cds 里为按钮与状态徽标补注解：

// app/books/annotate.cds —— Action 与状态显示
using CatalogService as service from '../../srv/cat-service';

annotate service.Books with @(
  UI : {
    LineItem : [
      { Value : 'title', Label : '书名' },
      { Value : 'stock', Label : '库存' },
      { Value : 'stock', Label : '状态',
        Criticality : 'criticality' }        // ← 库存映射为颜色徽标（见下）
    ],
    HeaderInfo : { TypeName : 'Book', TypeNamePlural : 'Books' }
  }
);

// 状态字段：把库存映射成「充足/紧张/售罄」三档颜色
annotate service.Books with @(
  Criticality : { StockCriticality }         // ponytail: 示例用计算属性，生产建议在服务端 handler 计算
);

// 或者用 UI.DataPoint 把数值字段渲染成带状态的徽标：
annotate service.Books with @(
  UI.DataPoint #stock : {
    Value : 'stock',
    Criticality : 'criticality',
    CriticalityLabels : [
      { Criticality : 3, Text : '售罄' },
      { Criticality : 2, Text : '紧张' },
      { Criticality : 1, Text : '充足' }
    ]
  }
);
💡 Criticality 说明 Criticality 接受 0–3 数值（或计算字段），Fiori Elements 据此给单元格/徽标上色：3=红（售罄）、2=橙（紧张）、1=绿（充足）。示例里的 criticality 是演示用计算字段，真实项目建议在服务端 handler 里算出返回，保证列表与详情一致。

F4.2 RAP 侧：CDS @UI 注解与 Draft

RAP 里 Fiori Elements 的注解写在 CDS 视图本身（消费视图 ZC_TRAVEL 或独立的元数据扩展），Service Binding 选 OData V4 – UI 后一键 Preview（详见 RAP 手顺4）。典型注解：

@UI: {
  headerInfo: {
    typeName: 'Travel',
    typeNamePlural: 'Travels',
    title: { type: #STANDARD, value: 'TravelID' },
    description: { type: #STANDARD, value: 'CustomerID' }
  },
  lineItem: [
    { value: 'TravelID', label: '旅行社', qualifier: #KEY },
    { value: 'AgencyID', label: '机构' },
    { value: 'CustomerID', label: '客户' },
    { value: 'Status', label: '状态', criticality: 'Criticality' }
  ],
  selectionFields: ['TravelID', 'CustomerID', 'Status']
}
@Search.searchable: true
define view entity ZC_TRAVEL as select from ZI_TRAVEL { ... }
  • 语法异同：RAP 用 @UI.headerInfo（驼峰），CAP 用 UI.HeaderInfo（点分）——但字段名一一对应（lineItem / LineItem、selectionFields / SelectionFields）。
  • Draft 机制：RAP 的 managed behavior 默认启用 Draft——点「编辑」先进入草稿（draft 状态），保存才落库。CAP 侧可用 @Common.DraftRoot 注解获得同类行为，但默认不启用。
  • 状态徽标：RAP 中 criticality 由行为实现里的 determination 计算（把 OverallStatus 映射为 0–3），与 CAP 的 handler 思路一致。

F4.3 RAP vs CAP 的 Fiori 实现对照

环节RAPCAP
注解语法CDS 视图 @UI.xxx（元数据扩展可分层）annotate.cds 的 @(UI.xxx)
生成/预览Service Binding（OData V4 – UI）→ Previewcds add fiori → /app/books/index.html
Action 按钮BDEF action + 实现类，自动出现在对象页service action + handler，自动出现在对象页
状态徽标criticality determination（EML）UI.DataPoint / 计算字段 + handler
编辑模式Draft（默认，managed）直接编辑；Draft 需 @Common.DraftRoot
🎯 一句话总结 Fiori Elements 不关心数据来自 RAP 还是 CAP——只认 OData 服务 + @UI 注解。RAP 把注解写进 CDS 视图，CAP 把注解叠在 annotate.cds；谁的后端暴露服务，谁就提供「门面」。

F4.4 操作手顺

  1. 确认服务 Action

    检查 srv/cat-service.cds 有 submitOrder（素材包已含），cds watch 下可用 curl 触发一次验证（见 CAP 手顺4）。

  2. 加状态徽标注解

    在 annotate.cds 按 F4.1 添加 UI.DataPoint #stock 与 CriticalityLabels，刷新列表核对徽标颜色。

  3. 点对象页「下单」

    进入任意有库存的书对象页，点「下单」按钮，确认触发 submitOrder、库存减少、Orders 新增一条。

  4. RAP 侧对照（可选）

    在 ADT 里给 ZC_TRAVEL 补 @UI.headerInfo / lineItem 注解，重新激活后在 Service Binding 点 Preview，对照 F4.3 表格观察同与不同。
