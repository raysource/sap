第 5 章：手顺3 —— 业务逻辑实现

用 srv/cat-service.js 注入事件处理，给服务添加业务规则

模型与服务是「声明式」的，业务规则（参数校验、库存校验、下单、日志）需要命令式代码。CAP 用 srv/*.js 文件以事件处理器的方式注入逻辑：写一个与 cat-service.cds 同名的 cat-service.js，导出函数即可自动注册。本章覆盖 CAP 开发的五大核心：校验、before 事件、after 事件、自定义 Action/Function、事务。

srv.before srv.on srv.after SELECT / UPDATE / INSERT req.reject Action / Function 事务

5.1 CAP 事件模型

每次 OData 请求都会按固定顺序经过三类事件处理器，你可以在任意阶段插入自定义逻辑：

  • srv.before(事件, 实体, handler)：在框架处理之前执行，适合鉴权、参数校验、日志。除了实体事件（CREATE / UPDATE / DELETE / READ），也适用于自定义 Action / Function（如 srv.before('submitOrder', ...)），本章 5.4 有完整示例。
  • srv.on(事件, 实体, handler)：替换或补充框架的默认处理，业务核心逻辑通常写在这里。handler 接收 req（请求对象，含 req.data、req.query），返回结果会作为响应体。
  • srv.after(事件, 实体, handler)：在框架处理之后执行，handler 接收 each（读出的每行结果，可改写）或 results（数组），用于结果加工、填充计算字段。
  • srv.emit(事件, 数据)：服务内部触发自定义事件，可配合 srv.on 形成松耦合的扩展点。
事件处理顺序
① 客户端请求 — READ / GET / POST submitOrder

5.2 扩展模型：订单实体 Orders

为了演示下单 Action，先给 db/schema.cds 追加一个 Orders 实体。这次用 cuid 生成 UUID 主键，与前面 Integer 主键形成对照：

// db/schema.cds —— 追加订单实体（追加到文件末尾）
entity Orders : cuid {
  book     : Association to Books;
  quantity : Integer;
  total    : Decimal(9,2);
  status   : String(16) default 'pending';
}
  • Orders : cuid：cuid 是 CAP 公共类型，自带 ID : UUID 主键、createdAt、createdBy、modifiedAt 等审计字段，写入时自动填充，无需手工维护。
  • book : Association to Books：订单关联到图书，外键列自动生成为 book_ID。
  • status default 'pending'：字段默认值。

5.3 声明 Action 与 Function

把 srv/cat-service.cds 更新为：启用 Orders 投影，声明自定义 Action submitOrder 与自定义 Function stockOf：

// srv/cat-service.cds —— 加入 Orders 投影、submitOrder Action 与 stockOf Function
using { sap.capire.bookshop as my } from '../db/schema';

service CatalogService {
  @readonly entity Books   as projection on my.Books;
  @readonly entity Authors as projection on my.Authors;
  @readonly entity Genres  as projection on my.Genres;
  @readonly entity Orders  as projection on my.Orders;

  action   submitOrder(book: Books, quantity: Integer) returns Integer;
  function stockOf(book: Integer) returns Integer;
}

action submitOrder(book: Books, quantity: Integer) returns Integer;：声明一个名为 submitOrder 的 Action，接收图书（引用 Books 实体，实际传 ID）与数量，返回一个整数（成功时返回下单数量）。客户端通过 POST /odata/v4/catalog/submitOrder 调用。

function stockOf(book: Integer) returns Integer;：声明一个名为 stockOf 的 Function，按 ID 查询图书当前库存。客户端通过 GET /odata/v4/catalog/stockOf(book=1) 调用——注意 Function 的参数写在 URL 括号里，而不是请求体。

🧭 Action vs Function
  • Action：POST 调用，允许副作用（写数据），适合下单、审批这类会改变状态的业务操作。
  • Function：GET 调用，约定只读、无副作用，适合查询类操作（查库存、算价格）。
  • 两种参数写法：book: Books（实体引用，客户端传 ID 即可）与 book: Integer（标量）效果等价，选一种即可，本章混用两种以作对照。

5.4 实现业务逻辑 srv/cat-service.js

新建 srv/cat-service.js，文件名与 cat-service.cds 同名（不含扩展名），CAP 自动把导出的函数绑定为该服务的处理器。完整代码：

const cds = require('@sap/cds')

module.exports = (srv) => {
  srv.on('READ', 'Books', (req) => {
    console.log('-> Reading books...')
  })

  // ① before：在 on 之前执行 —— 参数校验（同样适用于 CREATE/UPDATE 等实体事件）
  srv.before('submitOrder', (req) => {
    const { quantity } = req.data
    if (!Number.isInteger(quantity) || quantity <= 0) {
      return req.reject(400, `quantity must be a positive integer, got: ${quantity}`)
    }
  })

  // ② on：核心业务逻辑 —— 库存规则校验 + 多步写入（同一事务，任一步失败全部回滚）
  srv.on('submitOrder', async (req) => {
    const { book, quantity } = req.data
    const { Books, Orders } = cds.entities
    const bookRecord = await SELECT.one.from(Books).where({ ID: book })
    if (!bookRecord) return req.reject(404, `Book #${book} not found`)
    if (quantity > bookRecord.stock) {
      return req.reject(400, `${quantity} exceeds stock for book #${book}`)
    }
    await UPDATE(Books).set({ stock: bookRecord.stock - quantity }).where({ ID: book })
    await INSERT.into(Orders).entries({ book_ID: book, quantity, total: bookRecord.price * quantity })
    return { updated: quantity }
  })

  // ③ function：GET 语义的自定义函数 —— 只读、无副作用
  srv.on('stockOf', async (req) => {
    const { book } = req.data
    const bookRecord = await SELECT.one.from(cds.entities.Books).where({ ID: book })
    return bookRecord ? bookRecord.stock : 0
  })

  // ④ after：读完之后逐行加工结果
  srv.after('READ', 'Books', (each) => {
    if (each.stock > 100) each.title += ' -- 畅销'
  })
}

各段代码的作用：

  • srv.on('READ', 'Books', ...)：注册读取 Books 的事件处理器。这里只打日志（不返回值），框架仍执行默认读取。每次 GET 图书都会在终端打印 -> Reading books...。
  • ① srv.before('submitOrder', ...)：在 on 处理器之前执行，做参数校验——数量必须是正整数，否则 req.reject(400, ...) 立即中断请求。before 也适用于实体事件：srv.before('CREATE', 'Orders', ...) 会在框架插入订单前拦截，典型用法是校验必填字段、外键是否存在、写审计日志。
  • ② srv.on('submitOrder', ...)：核心业务逻辑。先查库做业务规则校验（库存充足性——依赖数据库状态，所以必须在 on 里查库判断），再执行两步写：UPDATE 扣减库存 + INSERT 生成订单。两步在同一事务里，见 5.6。
  • req.reject(404/400, ...)：抛出 OData 错误响应（HTTP 状态码 + 消息）并回滚事务。404 表示资源不存在；400 表示参数或业务规则不合法。带 return 是为了立即停止后续代码。
  • ③ srv.on('stockOf', ...)：Function 的处理器，与 Action 用同一个 srv.on 注册。从 req.data 取参数，返回一个标量（库存数）作为响应体。
  • ④ srv.after('READ', 'Books', (each) => ...)：读取后对每一行结果做加工——库存大于 100 的书在标题后追加「-- 畅销」。each 是单行结果对象，直接改写其字段即可；批量场景用 (results) => 接收整个数组。
  • const { Books, Orders } = cds.entities：cds.entities 是全部领域实体的注册表（数据层），SELECT / UPDATE / INSERT 都通过它访问实体做读写。
  • module.exports = (srv) => {...}：文件导出函数，CAP 启动时调用并注入服务实例 srv，你的处理器都挂在其上。

5.5 校验（Validation）

CAP 里校验分声明式和命令式两层，从简单到复杂按需选择：

  • 声明式（模型注解，零代码）：在 .cds 模型里用 @assert 标注约束，框架自动校验、自动返回 400，无需写 handler。适合与数据库状态无关的字段规则：
// db/schema.cds —— 声明式校验：quantity 必须介于 1~100，框架自动拦截
entity Orders : cuid {
  book     : Association to Books;
  quantity : Integer @assert.range : [1, 100];
  total    : Decimal(9,2);
  status   : String(16) default 'pending';
}
  • 命令式（handler 里 req.reject）：需要查库、跨字段或与业务状态相关时，在 before / on 处理器里手动校验。分工惯例：
    • before：参数格式、必填项、鉴权——只依赖请求本身，不依赖数据库（5.4 里 quantity 的正整数校验）。
    • on：业务规则——必须查库才能判断的，如库存充足性（5.4 里 submitOrder 的库存校验）。
  • req.reject 状态码速查：400 参数不合法 / 403 无权限 / 404 资源不存在 / 409 状态冲突。reject 会立即中止请求并回滚事务（见 5.6）。

5.6 事务（Transaction）

CAP 把每个请求自动包裹在一个数据库事务里：处理器正常返回 → 自动 commit；任何处理器抛出错误或调用 req.reject → 自动 rollback。你不需要手写 begin / commit / rollback。

为什么重要：5.4 的 submitOrder 包含两步写——UPDATE 扣库存、INSERT 生成订单。没有事务的话，任一步失败都会留下「库存扣了但订单没生成」的半成品数据。放在同一个请求（同一个事务）里，要么两步都成功，要么都回滚。

  • 事务边界 = 一个请求：before → on → after 全程在同一个事务里，跨 handler 的读写彼此可见。
  • 验证回滚：把 submitOrder 里的 INSERT 故意改成写一个不存在的字段（或直接 return req.reject(500, 'boom')），再下一次单——你会看到库存没有减少，因为 UPDATE 和 INSERT 一起回滚了。
  • 手动控制（一般用不到）：req.tx 可拿到当前事务对象；const tx = await cds.tx(req) 可另开事务，配合 await tx.commit() / await tx.rollback() 做细粒度控制。日常开发交给默认行为即可。

⚠️ handler 编写注意事项
  • 文件位置与命名：JS 文件必须在 srv/ 下，且与 .cds 服务文件同名（如 cat-service.cds ↔ cat-service.js），否则不会自动注册。
  • 避免阻塞：handler 里不要写同步的耗时操作（大循环、同步文件读写），会阻塞 Node.js 事件循环；用 async/await 写异步逻辑。
  • 改动生效：修改 *.js 后 cds watch 会自动重启生效；但修改 *.cds（模型结构）后建议手动重启一次，避免数据库结构未刷新。
  • SELECT 的写法：示例中 SELECT.one.from(cds.entities.Books) 与 const { Books } = cds.entities 后 SELECT.one.from(Books) 等价，二选一即可。
