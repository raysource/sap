第 1 章：CAP 概述

Cloud Application Programming Model · 云原生企业应用的「乐高积木」

CAP 是 SAP 开源的全栈云应用框架：用一套 CDS 领域模型同时驱动数据、服务、UI 三件套，用 Node.js（或 Java）写业务逻辑，几分钟内就能启动一个带 OData 接口、可连 Fiori 的应用。

Node.js CDS 模型 OData V4 本地 SQLite BTP Cloud Foundry

1.1 CAP 是什么

CAP（Cloud Application Programming Model）是 SAP 针对云开发的领域驱动框架，核心理念是「以 CDS 领域模型为中心，自动生成一切可以自动生成的东西」：

① 单一领域模型

在 db/schema.cds 里用 CDS 声明实体、类型、关联。数据库表由框架自动生成。

② 声明式服务

在 srv/*.cds 里声明 service，OData V4 接口与 UI 注解自动暴露，无需手写路由。

③ 可插拔后端

本地开发用 SQLite，生产切 HANA Cloud / PostgreSQL；用 srv/*.js 注入自定义逻辑。

1.2 运行时与项目结构

一个典型 CAP 项目只有三个顶层目录，每个都有明确职责：

bookshop — 项目结构
▾📁 bookshop/
▾📁 app/ ← Fiori / UI5 前端应用
📄 books/（Fiori Elements List Report）
▾📁 db/ ← 数据模型 + 种子数据
📄 schema.cds
▸📁 data/（CSV 初始数据）
▾📁 srv/ ← 服务定义 + 业务逻辑
📄 cat-service.cds
📄 cat-service.js
📄 package.json
📄 .cdsrc.json
📄 README.md
图 1-1 CAP 项目三目录：app（前端）/ db（数据）/ srv（服务）

数据流非常直观：CDS 模型 → 运行时（Node.js）→ OData V4 / REST → Fiori Elements。开发时 cds watch 会启动本地服务器（默认 localhost:4004）并实时重载：

$ cd bookshop
$ cds watch
[cds] - serving CatalogService { path: '/odata/v4/catalog' }
[cds] - server listening on http://localhost:4004
[cds] - using bindings from: { registry: '~/.cds-services.json' }
[cds] - connect to http://localhost:4004/odata/v4/catalog ...
 
$ curl http://localhost:4004/odata/v4/catalog/Books
{ "value": [ { "ID": 1, "title": "Wuthering Heights", ... } ] }

1.3 培训场景：书店 Bookshop

CAP 官方参考场景 Bookshop，模型非常贴合真实业务：

实体说明关键字段
Authors作者主数据ID, name, dateOfBirth
Genres图书分类ID, name, descr
Books图书（核心实体）ID, title, author(关联), stock, price, currency

配套一个 CatalogService 服务，只暴露 Books 的投影并标注 @readonly，体现「一个模型、多个服务视图」的最佳实践。

1.4 CAP vs 传统全栈开发

维度手写 Express + REST + UI5CAP 框架
模型定义数据库表 + ORM + DTO 各写一遍一份 schema.cds，表 / OData / UI 注解全自动
接口手写路由、序列化、校验OData V4 自动生成（含 $metadata）
数据访问ORM 手工 CRUDCDS 查询语言 + 自动 CRUD
测试逐接口写测试夹具cds watch + SQLite 种子数据秒级可测
部署手动配置容器 / CFcds build + MTA 一键打包部署
🤔 RAP 与 CAP 怎么选？ 想复用到 S/4HANA 内的数据与业务对象 → 用 RAP；想在云上从零构建、快速迭代、面向非 SAP 数据源 → 用 CAP。两者可以联动：CAP 应用可通过 OData 消费 RAP 服务。回到首页对比表查看逐维度对比。
