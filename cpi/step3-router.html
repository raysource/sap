第 I5 章：手顺3 —— 内容路由

Exchange Property + XPath → Content-Based Router：按订单类型把消息送进不同的处理分支

集成里的第二大类需求是分流：同一入口进来的消息，按内容不同走不同处理——普通订单走标准通道，加急订单要打上优先级标记；邮件、订单、发票也许来自同一个文件目录但要发去三个系统。本章做一个「订单分流」iFlow：读取 XML 订单里的 <type>，用 Content-Based Router（CBR） 把 urgent 的订单与其它订单分开，各自打上不同的请求头再转发——通过回显的 header 验证消息确实走了对应分支。

Exchange Property XPath Content-Based Router 多分支 XML

I5.1 为什么先要「属性」

路由器判断的对象不是 body 本身，而是条件——条件基于消息的 header 或 exchange property（I4.1 的三件套）。所以标准套路是两步：

  1. 用一个步骤把「要据以分流的业务值」抽出来存进 property（通常用 Content Modifier 的 XPath，或 Groovy）；
  2. 路由器按 property 值判断走哪个分支。

为什么存 property 而不是直接在路由里写 XPath？因为 property 是「名字化」的中间结果——名字清晰、可复用（下游任何步骤都能读 ${property.orderType}）、路由配置也更简单。这与编程里「先算个局部变量再 if」是同一个道理。

💡 判定用 header 还是 property？ 入站请求头（如调用者传的 X-Priority）→ 直接按 header 判；body 里解析出来的业务值 → 先存 property 再判。别把内部计算结果塞进 header 传给外部系统，除非对方确实需要。

I5.2 Content-Based Router 怎么配

CBR 是一个「多出口」步骤：每条路由（Route）配一个条件（属性/头 + 运算符 + 值），从上往下匹配，命中即走该分支；都不命中走 Default 分支。相邻概念顺带分清：Router 是单条件二选一，CBR 是多条件多分支，Multicast 则不分流而是广播（每个分支都执行）。

步骤行为适用
Router一个条件：满足 → 分支 A；否则 → Default简单二选一（如是否空值）
Content-Based Router多个条件依次匹配，命中一条走一条订单按类型/区域/渠道分多路（本章）
Multicast不分流，同一条消息发往所有分支一个事件要同步通知多个系统

</order>

I5.4 操作手顺

  1. 新建 iFlow：order-dispatch

    包 iflow_course → Add → Integration Flow，命名 order-dispatch。

  2. Sender

    HTTPS，Address /dispatch。

  3. Content Modifier：抽 orderType 属性

    添加 Content Modifier（命名 ExtractType）→ Exchange Property 区加一行：Name orderType、Type XPath、Value /order/type。作用：入站 XML 的 <order><type>… 被抽成流内属性。

  4. Content-Based Router：两分支

    添加 Content-Based Router（命名 RouteByType），配两条路由：

    • Route 1：条件「Property orderType = urgent」（条件面板里选属性、填运算符与值，无需写代码）；
    • Default：其它全部。

  5. 分支内打标 + 各自 Receiver

    Route 1 分支：Content Modifier（MarkUrgent）→ Header X-Route = urgent → Receiver（HTTP echo，名 ReceiverUrgent）。Default 分支同样结构：Header X-Route = normal → ReceiverNormal。两个 Receiver 的地址都用 https://postman-echo.com/post（名字不同即可）。

  6. 部署 + 分别测两条路

    # ① 普通订单（预期走 Default，回显 headers.x-route == normal）
curl -s -X POST "<ENDPOINT>" -H 'Content-Type: text/xml' \
  --data-binary @order-normal.xml | python3 -m json.tool

# ② 加急订单（预期走 Route 1，回显 headers.x-route == urgent）
curl -s -X POST "<ENDPOINT>" -H 'Content-Type: text/xml' \
  --data-binary @order-urgent.xml | python3 -m json.tool

I5.5 验证：看回显 header 与 MPL 分支

  • 回显验证：两次调用响应里的 headers.x-route 分别为 normal / urgent——证明消息走了不同分支、打了不同的标。
  • MPL 验证：Monitor → Message Processing Log → 点开加急订单那次，流程轨迹里能看到 Router 节点后接的是 MarkUrgent（而不是另一侧步骤）；普通订单那次则相反。
MPL — 加急订单（ORD-2002）流程轨迹
✓ Sender（HTTPS /dispatch）— 接收 order-urgent.xml
✓ ExtractType — property orderType = urgent
✓ RouteByType — 命中 Route 1（orderType == 'urgent'）
✓ MarkUrgent — Header X-Route = urgent
✓ Receiver (Urgent) — HTTP 200
对比：传 order-normal.xml 时，Router 行显示「命中 Default」，后续轨迹是 MarkNormal → Receiver (Normal)
图 I5-2 MPL 轨迹能直接看出消息命中了哪条路由、走了哪个分支——路由类问题都在这里对答案

I5.6 注意

  • XML 命名空间：本章样例为了聚焦路由逻辑用了无命名空间的 XML。真实 XML 几乎都带默认命名空间（如 <order xmlns="http://acme.com/order">），此时 XPath 必须带前缀：在 Content Modifier 的 XPath 面板里给命名空间起前缀（如 ns1），值写 /ns1:order/ns1:type。路由条件同理。
  • 条件区分大小写：'urgent' 不会匹配 'Urgent'。数据源不可控时，先在 Groovy/Content Modifier 里统一小写再存属性。
  • 空值陷阱：入站 XML 缺 <type> 时 XPath 得到空串，会走 Default——通常这正是想要的兜底。
  • Receiver 重名：同一 iFlow 内 Receiver 名称不能重复，所以上面用了 ReceiverUrgent / ReceiverNormal。
✅ 本章验收标准 你能：① 说出为什么先抽 property 再路由；② 用两张测试 XML 各调一次，回显 header 分别正确；③ 在 MPL 轨迹里看到命中的分支；④ 解释带命名空间 XML 时 XPath 怎么改。
