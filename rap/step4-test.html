第 6 章：手顺4 — Fiori 预览与测试

Fiori Elements List Report · 增删改 · Action · OData 直连测试

手顺 1-3 已经产出一个 OData V4 服务。本章在 Fiori Elements 里完整走一遍业务流：预览列表、创建、编辑（Draft）、批准/拒绝，再用 POSTMAN 直接验证 OData 增删改查。

Fiori Elements List Report Object Page Draft OData CRUD

6.1 预览 Fiori List Report

在 Service Binding（手顺3）点击 Preview（或右键服务 → Preview），浏览器打开 Fiori Elements 的 List Report——列表页。顶部是标题与搜索，下方是筛选栏、工具栏与数据表格：

6.2 创建新记录

点工具栏 创建，弹出创建对话框，填写客户、日期、金额等信息后点 保存。新行以状态 N 新 出现在列表顶部：

6.3 编辑与 Draft（草稿）

点击某行进入 Object Page 对象页。点 编辑 后进入编辑模式——注意此时数据写入的是草稿表，顶部状态徽章旁会显示「草稿」标记；不点保存、直接返回，正式数据不会被改动：

6.4 执行 Action：批准 / 拒绝

选中一行，点 批准，弹出确认对话框；确认后调用后端 AcceptTravel Action，状态从 O 处理中 变为 A 已批准，列表对应行状态即时刷新：

6.5 用 POSTMAN 直接测试 OData

UI 背后其实是标准 OData V4 请求。用 POSTMAN（或 curl）可绕过 UI 直接验证，非常适合自动化回归。下面的 URL 以 d4h:8000 为例，实际替换为你的主机与端口：

查询（GET）

# 取前 5 条
GET http://d4h:8000/sap/opu/odata4/sap/zuiv4travel_o4/srvd/sap/zui_travel_o4/0001/Travel?$top=5

# 按状态筛选（已批准）
GET http://d4h:8000/sap/opu/odata4/sap/zuiv4travel_o4/srvd/sap/zui_travel_o4/0001/Travel?$filter=Status%20eq%20'A'

# 单条 + 展开子实体
GET http://d4h:8000/sap/opu/odata4/sap/zuiv4travel_o4/srvd/sap/zui_travel_o4/0001/Travel(1)?$expand=Booking

创建（POST）

POST http://d4h:8000/sap/opu/odata4/sap/zuiv4travel_o4/srvd/sap/zui_travel_o4/0001/Travel
Content-Type: application/json

{
  "AgencyID": 1,
  "CustomerID": 3,
  "BeginDate": "2026-09-15",
  "EndDate": "2026-09-25",
  "TotalPrice": "5600.00",
  "CurrencyCode": "EUR",
  "Status": "N",
  "Description": "十一黄金周东京之旅"
}

响应 201 Created，Location 头指向新记录，例如 /Travel(7)。

更新（PATCH）与删除（DELETE）

# 更新状态为 O（处理中）——注意：开启 draft 时更新走 DraftEntity，此处为直接 PATCH 示例
PATCH http://d4h:8000/sap/opu/odata4/sap/zuiv4travel_o4/srvd/sap/zui_travel_o4/0001/Travel(3)
Content-Type: application/json

{ "Status": "O" }

# 删除（响应 204 No Content）
DELETE http://d4h:8000/sap/opu/odata4/sap/zuiv4travel_o4/srvd/sap/zui_travel_o4/0001/Travel(3)

删除时若记录已批准且行为实现禁止删除，会返回 403 / 业务错误消息——这正是 4.4 节 get_features 与校验约束在起作用。

6.6 状态流转总结

状态说明触发动作可否删除
N 新刚创建，可自由编辑创建✅ 可
O 处理中（Open）已开始处理/被编辑过更新（PATCH）✅ 可
A 已批准（Approved）业务批准通过AcceptTravel❌ 视实现拒绝
X 已拒绝（Rejected）业务被拒绝RejectTravel✅ 可

6.7 操作手顺

  1. 打开 Preview

    在 Service Binding 点 Preview（或右键服务 → Preview），浏览器打开 Fiori List Report。

  2. 创建一条旅行

    点 创建，填客户/旅行社/日期/金额/描述，保存。确认新行状态为 N 新。

  3. 编辑进入 Draft

    打开该行对象页 → 编辑，改描述后不保存直接返回；再进入确认正式数据未变，理解 Draft 机制。

  4. 执行批准 Action

    选中一行状态 O 的记录 → 批准 → 确认，列表状态变 A 已批准；批准后再点批准，按钮应置灰（get_features 生效）。

  5. POSTMAN 测 OData

    按 6.5 节依次执行 GET / POST / PATCH / DELETE，核对状态码与返回 JSON。

✅ 验证/结果 全部 CRUD 与 Action 在 UI 与 POSTMAN 双通道跑通；$filter、$top 生效；状态流转 N → O → A / X 符合 6.6 节表格。
💡 注意点
  • Draft 与正式数据：编辑未保存时，OData 层访问的是草稿实体（DraftEntity），正式表数据不变；丢弃草稿可调用 Cancel 操作。
  • 权限不足：若 Preview 或请求返回 403，检查用户 PFCG 角色是否含 ZI_TRAVEL 对应授权（authorization master 起了作用）。
  • Fiori 运行时：Preview 依赖系统已激活 Fiori BSP 运行时（/sap/bc/ui5_ui5 等）；若空白，先在事务 SICF 激活对应节点。
  • UI 注解：本培训未加 @UI 注解，Fiori 用默认布局渲染；真实项目通过消费视图的 @UI 注解定制列、筛选与 facets。

答案与解析（🟢 基础巩固（1–8））
题号答案解析
1B绑定对象上直接启动 Fiori Elements 预览，浏览器即可见 List Report。
2B页面结构由注解驱动：改注解即改 UI，这是 RAP × Fiori 的主线思想。
3B草稿模式下新增先建 Draft 记录，激活（保存并提交）后才可见于正式查询。
4B已到终态的实例不允许再流转，UI 层通过 features 禁用对应按钮。
5A$top 是 OData 的限量查询选项，此处取前 5 条验证列表读取。
6A创建成功通常返回 201 Created 并带 Location 头指向新实体。
7BPATCH = 部分更新，PUT = 整体替换；对 RAP 实体日常用 PATCH 更安全。
8BPostman 面向 API 契约本身：适合验证 draft 通道、Action、过滤与错误返回，可留作接口回归。

答案与解析（🔶 能力提高（9–12））
题号答案解析
9B草稿代理了编辑：UI 的保存先写草稿，激活才合并；绕过草稿直改正式数据违背该机制。

12A$filter 是 OData 的过滤语法：字段 eq 值。
